## Context

See proposal.md — Why. The constraint that shapes the approach is where tide's configuration actually lives on a machine running this repository. Tide reads plain `tide_*` variables, and there are two sets of them: the universals in `fish_variables`, which is ignored here, and the globals in `.config/fish/conf.d/tide.fish`, which is tracked and is re-set on every shell start. `conf.d` runs after universals are loaded, so the tracked globals shadow the universals — the tracked file always wins, which is the point of it existing.

`conf.d/tide.fish` is generated by `tide-save-config`, which dumps this machine's universals. So the two sets are not independent: editing one without the other either has no effect or is silently reverted the next time the file is regenerated.

## Goals / Non-Goals

**Goals:**

- The item is gone for every clone, not only for this machine.
- The committed file stays a faithful dump of the universals, so the next unrelated `tide-save-config` produces no incidental drift.

**Non-Goals:**

- Changing direnv, its hook, or when environments activate.
- Reviewing the rest of `tide_right_prompt_items`. Most of its entries are for toolchains not installed here and draw nothing; they cost nothing and are not what this change is about.

## Decisions

**Set the universal, then regenerate the file — rather than editing `conf.d/tide.fish` directly.** A direct edit is correct until the next `tide configure` or `tide-save-config`, which dumps the universals and writes `direnv` straight back. Setting the universal first makes the tracked file and the machine agree, so regeneration is idempotent. This is the same order the `restyle-vi-mode-prompt-icons` change used, and the file's own header states the rule.

Note the corollary, because it is the failure this change was first hit by: setting only the universal appears to do nothing. The global from `conf.d` shadows it in every new shell, so the prompt is unchanged and the edit looks ineffective. Universal first, file second — but the file is what takes effect.

**Regenerate `_tide_right_items` too.** Tide caches a machine-filtered copy of the item list in `_tide_right_items`, dropping items whose tool is absent. A shell that already holds the old cache keeps drawing the old prompt; `_tide_cache_variables` or a fresh shell refreshes it. This is session state, not configuration, and nothing is committed for it.

**Keep `tide_direnv_bg_color`, `tide_direnv_color`, `tide_direnv_color_denied`, and `tide_direnv_icon`.** They describe how the item looks if drawn, and cost nothing while it is not. Removing them would mean re-choosing a glyph and two colours to reverse this change; keeping them makes the reversal one word in one list. They are also what `tide configure` would write back anyway.

## Risks / Trade-offs

- **The `▼` also signalled a denied `.envrc`, in red, and that signal is now gone.** → direnv still prints its own line naming the blocked file and the `direnv allow` needed, on entering the directory and on every shell started there. The prompt item was the quieter of the two reports, and the loud one remains. The `python-venv-activation` spec already requires that an unapproved declaration be reported, and that requirement is met by direnv's own output, not by the prompt.
- **A machine that pulls this while a fish session is open keeps drawing `▼` until that session restarts.** → Cached prompt state, not a configuration error; it resolves on the next shell.
